# TravelMate AI — Security

Status: Draft v0.1 (Milestone 0). Section numbers are referenced from `docs/ARCHITECTURE.md`.

Principles:
1. No money moves without a named human's explicit approval of a specific quote.
2. Data from providers and users is untrusted until validated.
3. Secrets never enter the repository, logs, fixtures, or API responses.
4. Failure closes the path: when in doubt, the system does not book.

## 1. Secret management and environment variables

Secrets in the MVP include: `OPENAI_API_KEY`, database passwords, and future provider credentials.

Rules:
- Secrets are read only from environment variables, loaded by the typed settings module (`app/config.py`). No code reads `.env` directly.
- `.env` files are never committed. `.gitignore` excludes `.env` and `.env.*` and keeps `.env.example`.
- `.env.example` contains variable **names** and obviously fake placeholders (for example `OPENAI_API_KEY=replace-me`). It never contains a real value.
- Secrets are not hard-coded, not stored in fixtures, and not placed in documentation, issue text, or commit messages.
- Secrets are masked in configuration dumps. The settings object's `repr` never prints secret values.
- Local development uses a developer's own key. CI uses no real key; tests use fakes.
- If a secret is committed by mistake, it is revoked and rotated immediately. Removing it from history is not sufficient on its own.

Required configuration (names only):

| Variable | Secret | Default | Purpose |
|---|---|---|---|
| `APP_ENV` | No | `development` | Environment name. |
| `DATABASE_URL` | Yes | none | PostgreSQL connection string. |
| `OPENAI_API_KEY` | Yes | none | LLM provider key. |
| `LLM_MODEL` | No | set in config | Model identifier. |
| `PROVIDER_MODE_TRANSPORT` | No | `mock` | `mock` or `live`. |
| `PROVIDER_MODE_HOTEL` | No | `mock` | `mock` or `live`. |
| `PROVIDER_MODE_WEATHER` | No | `mock` | `mock` or `live`. |
| `BOOKING_ENABLED` | No | `false` | Master switch for booking execution (see §4). |
| `LOG_LEVEL` | No | `INFO` | Logging level. |

Startup validation: the application refuses to start if `APP_ENV=production` and any required secret is missing, or if `BOOKING_ENABLED=true` without the approval flow enabled.

## 2. Authentication and authorization

Status of this section: **requirements for the design; the mechanism is unresolved (PRD Q4).**

- Every endpoint except health checks requires an authenticated principal. In local development, a single developer principal may be configured explicitly. Anonymous access is never the default.
- Every trip, run, quote, itinerary, booking intent and approval has an owner. Access checks compare the principal to the owner on every request. An ID in the URL is not sufficient.
- Approval requires a principal with the `approver` capability. In a single-user MVP, the owner may approve their own intent, and this is recorded in the audit log. Separation of duties is a requirement for any multi-user release.
- Authorization checks live in the service layer, not in route handlers alone, so every entry point is covered.
- Tokens are short-lived. Tokens are never placed in URLs or logs.
- Rate limits apply to planning runs and approval endpoints to limit cost and abuse. The limit values are set when Q4 is resolved.

## 3. LLM prompt injection and untrusted provider data

The LLM reads text that the user and providers control: trip notes, hotel descriptions, reviews, and provider error messages. Any of these can contain instructions intended to change the agent's behaviour.

Controls:
1. **Separation of data and instructions.** Untrusted text is passed inside clearly delimited data blocks, and the system prompt states that content inside those blocks is data, not instructions.
2. **Structured outputs only.** The LLM returns typed objects validated by Pydantic. Free-text output is never executed or used as a tool argument without validation.
3. **No privileged tools for the LLM.** Tools available to the LLM are read-only research functions and a constrained itinerary writer (ARCHITECTURE §4). None can create bookings, change approvals, read secrets, or access other users' data.
4. **Authority comes from code, not text.** An LLM response saying "the booking is confirmed" or "approval is granted" has no effect. Booking state changes only through service code with the validations in §4 and §5.
5. **Figures are not generated by the LLM.** Prices, availability, dates and totals come from providers or deterministic code. The LLM may describe them.
6. **Output checks.** Itinerary text is checked for references to option IDs that exist in the run. Unknown IDs cause a validation error.
7. **Provider data is validated.** Responses are parsed into strict models. Unexpected fields are dropped. URLs are not fetched automatically from provider content.
8. **Limits.** Maximum tool calls, steps, and tokens per run (NFR-09) bound the damage of a manipulated loop.
9. **Testing.** A test suite includes injection strings in hotel names, reviews and user notes, and asserts that no booking or approval state changes and no tool outside the allowed set is called.

## 4. Human approval requirements for booking and payment

- **Default off.** `BOOKING_ENABLED=false`. In the MVP, no booking client is called and no payment is attempted, regardless of input. This is verified by a test that spies on the booking client (AC-05).
- **Explicit approval per quote.** An approval records the approver, the time, and the `quote_content_hash` of exactly what was displayed (price, currency, options, fees, cancellation terms, traveller details).
- **Display before approval.** The UI shows the full total, currency, what is included, cancellation terms, the provenance of each price, and a plain statement that approving will attempt a real booking.
- **No agent approval.** No LLM, tool, or background job can create an approval.
- **Approval expiry.** Approvals expire after the period set by PRD Q7. An expired approval is not used.
- **Enablement is a deliberate change.** Turning on booking requires a code review of the booking executor, a reviewed configuration change, and a passing test suite that includes the approval and revalidation tests.
- **Simulated demo booking.** A clearly labelled simulation of a mock booking may exist (ADR 0003). It is a separate type and code path with no I/O, never uses `BookingIntent`, `Approval` or `CONFIRMED`, is not reachable by voice or by any LLM tool, and its reference is never a provider confirmation. It does not weaken the rules above: real booking stays off.
- **Payments.** Payment capture is not designed or implemented. Any future payment feature needs its own security review and an ADR before work starts (PRD Q8).

## 5. Price revalidation

Before any booking step:
1. Re-fetch the quote from the provider (LIVE) or re-check the mock quote (MOCK).
2. Compare the new quote's content hash with the approved hash. Compare amount, currency, option identifiers, fees, and cancellation terms.
3. If anything differs, or the quote is past `valid_until`, the intent returns to AWAITING_APPROVAL and the user is shown the change. No booking request is sent.
4. A revalidation that cannot be completed (provider error) also blocks the booking. It is never treated as "unchanged."

A mock quote in MOCK mode goes through the same comparison, so the path is tested even without live data.

## 6. Duplicate booking prevention

- Each booking execution attempt has an idempotency key derived from the booking intent ID and approval ID. The database enforces uniqueness (ARCHITECTURE §5, `booking_intents.idempotency_key`).
- A booking intent can move to BOOKING only once. The transition is a conditional update in one transaction, so two concurrent requests cannot both succeed.
- Provider calls that create bookings are never retried automatically unless the provider documents idempotency for that call. Ambiguous outcomes (timeout after sending) move the intent to NEEDS_REVIEW (ARCHITECTURE §6), not to FAILED or to a retry.
- The UI disables repeated submission after the first click and shows the existing status when the same intent is requested again.

## 7. Data minimization

- Collect only what planning needs: names as they appear on travel documents only if booking is later enabled, traveller count and ages where pricing requires it, dates, origin and destination, budget, and preferences.
- Do not collect passport numbers, government IDs, card numbers, or full dates of birth in the MVP. If a future feature needs them, it needs its own review and encryption design.
- Do not send unnecessary personal data to the LLM. Trip notes are sent only when needed for planning, and identifiers are replaced with run-scoped aliases where possible.
- Provider requests include only the fields the provider needs.
- Personal data in the database is deleted or anonymised when a user deletes a trip. Retention rules are finalised with Q4.
- Backups and exports are treated as sensitive.

## 8. Audit logs

- Audit events are written for: trip creation and deletion, planning run start and finish, provider mode changes, selections, itinerary versions, booking intent creation, quote revalidation outcomes, approvals and rejections, booking attempts (even when disabled), and authorization failures.
- Each event records: timestamp (UTC), actor (principal ID or `system`), event type, entity type and ID, request ID, and a redacted data payload.
- The audit table is append-only at the application level. Database permissions for the application role deny `UPDATE` and `DELETE` on `audit_events`. Corrections are recorded as new events.
- Audit payloads never contain secrets, full card data, or unredacted personal data beyond what the event needs (for example, the approved quote hash rather than the full traveller list).
- Audit retention period is set with Q4 and the privacy policy; until then, audit data is kept for development only.

## 9. Safe logging

- Logs are structured JSON. Each entry includes `request_id` and, where relevant, `run_id` and `trip_id`.
- A redaction filter removes or masks: API keys and tokens (including `Authorization` headers), passwords, connection strings, cookies, and fields named like `*secret*`, `*token*`, `*password*`, `*key*`, and any traveller personal-data field.
- Logs do not contain full LLM prompts or full provider responses. They log sizes, hashes, status codes and error codes. Full payloads are available only in a debug mode that is disabled in shared environments.
- Exception messages sent to clients are generic. Full details go to the server log with the request ID.
- A test asserts that a known fake secret does not appear in captured log output (AC-08).

## 10. Dependencies and supply chain

- Dependencies are pinned in the lock file and reviewed when added. The project avoids unmaintained or unnecessary packages.
- CI runs a dependency vulnerability audit and a secret-scanning tool. Tool choices are made in Milestone 1.
- Container images use slim base images and run as a non-root user.
- Third-party provider SDKs are wrapped by the adapter layer so they can be replaced or removed.

## 11. Reporting a security issue

- Report suspected vulnerabilities to the project owner privately. Do not open a public issue with exploit details.
- Include the affected component, steps to reproduce, and impact. Do not include real credentials or personal data in a report.
- If a secret may have been exposed, rotate it first, then investigate.

## 12. Voice sessions

Status: **foundation only.** No voice provider, audio or key exists. Decisions: ADR 0002 (architecture), ADR 0003 (demo booking is separate). Plan: `docs/VOICE_ASSISTANT_PLAN.md`.

What exists now:
- **Off by default.** The routes are mounted only when `VOICE_ENABLED=true`; a normal start has no voice routes. When on, every limit must be set explicitly (session length, idle timeout, concurrent sessions and sessions per day per owner). There are no hidden defaults.
- **Not in production.** The app refuses to start with voice enabled and `APP_ENV=production`, because voice needs real authentication (PRD Q4). Until then the API acts for one configured development principal (`VOICE_DEV_PRINCIPAL`), as §2 allows. Anonymous access is never the default.
- **Sessions.** An opaque random ID (256 bits), an absolute time limit that activity cannot extend, an idle timeout, and per-owner concurrent and daily limits. Sessions live in memory and are lost on restart. A session carries no audio.
- **Ownership.** Every lookup checks the owner. Another person's session, a missing one and an ended one are indistinguishable ("not found"). Error bodies never repeat an ID.
- **Tool allow-list.** A voice conversation may only ever use `search_transport`, `search_hotels` and `get_weather`, matched exactly. There is no booking, approval, payment or demo-booking tool, and a test fails if one appears.
- **Isolation.** The voice package may not import booking, workflow, the LLM layer, providers or any network library, and only the voice router and the app factory may import it.

Requirements for the milestones still to come (not built):
- No permanent provider key in browser code. Use a short-lived, narrowly scoped token minted by the backend, or a backend relay.
- Tell the user before the first use which third party processes the audio. The microphone is requested only after a user action.
- Do not store raw audio. Any retention needs the owner's approval, a retention period and a deletion path (§7). Logs follow §9 and never hold audio or full transcripts.
- Speech and transcripts are untrusted data (§3). Voice recognition is never authorisation: only the visible approval path in §4 can approve anything, and the voice layer has no approval tool.
- Usage caps and cost counting apply to every provider call (NFR-09).
