# TravelMate AI: project context

A short brief for starting a new working session. Update only the lines marked **UPDATE** after each commit; the rest rarely changes. It summarises the other documents and does not replace them: the PRD, ARCHITECTURE, SECURITY, the implementation plan and `CLAUDE.md` are the sources of truth.

## Project
- An Agentic AI travel planner, built as a portfolio project to learn Agentic AI engineering.
- Backend: Python 3.12, FastAPI, Pydantic v2, strict mypy, Ruff. Frontend: React 19, TypeScript, Vite.
- Planned and **not built**: LangGraph, a live LLM, PostgreSQL use, live providers, authentication, any booking.
- Repository: github.com/rishabhrathod12/TravelMate-AI, branch `main`.

## Decided by the owner (UPDATE as questions are answered)
- A trip request has an explicit `trip_type` (`ONE_WAY` or `ROUND_TRIP`). A same-day return is a round trip with the same date.
- The `budget` field and the `preferences` length cap are deferred. There is no traveller upper limit yet.
- The frontend prototype was approved, built ahead of the API, with demo data labelled MOCK.
- Q12 (2026-10-30): transport fares are per traveller; hotel prices are per room per night, with the basis carried on each quote.
- Q13 (2026-10-30): round trip has nights = return minus departure, a departure-to-return weather window and nights + 1 itinerary days. One-way and same-day trips have no hotel stay or total, a one-day weather window and a one-day itinerary.
- Q14 (2026-10-30): 1 to 9 travellers, preferences up to 500 characters, budget still deferred. In code since 2026-10-30 (domain model, provider queries, the search form and the chat endpoint).
- Q18 (2026-10-30): contingency 10% of transport, hotel and local-transport lines, rounded up; the local transport allowance is not applicable until the owner sets an amount.
- These four decisions are in code since 2026-10-30 (`quote.py`, `trip_rules.py`, `cost_policy.py`, `trip.py` and the search view). Still open inside them: the budget rule, the number of rooms per party (the estimate uses 1 room and says so), and the local transport allowance amount.
- Chat-first itinerary planning (2026-10-30, ADR 0004, PRD FR-19, not implemented): the chat becomes the main screen and writes a whole day-by-day itinerary from a message such as "plan my 5-day itinerary for Goa this weekend"; the search/comparison dashboard stays as an optional link. Relative dates ("this weekend") are resolved by code from a fixed list and confirmed by the traveller. Suggestions are labelled `AI_SUGGESTION`; no prices, hours, availability, travel times or weather as facts. Built first on the stand-in with a labelled scripted sample; a real model is a separate approved step (Q19, dependency, key, first live call). Phases C1 (relative dates), C2 (chat-first screen), C3 (real model, blocked).

## Working rules (rarely change)
- Read `CLAUDE.md` and `docs/` first. Stop at the end of each milestone.
- Never commit or push without the owner's explicit approval.
- Never invent live data. Label every provider value LIVE, CACHED_LIVE or MOCK. Money is integer minor units plus a currency code.
- Do not silently resolve open decisions: list them with a recommendation, and ask only what blocks safe work.
- Human approval is required before any real booking or payment. No secrets in files, logs or output.
